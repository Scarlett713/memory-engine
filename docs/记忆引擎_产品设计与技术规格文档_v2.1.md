二、产品形态说明
2.1 一套系统，通过账号类型差异化渲染
结论：机构端和个人端共用同一套代码库（Next.js 14），通过 userType 字段和设备类型进行条件渲染，差异化展示功能和UI。前端为同一套代码库，条件渲染双端UI；后端为统一API，通过 userType 区分业务逻辑。
理由如下：
维度
分析
团队规模
唯一前端开发者，两套代码库意味着所有功能改两遍、Bug 修两遍
功能重叠度
两端共用：音频上传、进度面板、AI处理、导出按钮、情感标记；差异仅在：项目创建表单、审校界面深度、导航布局
技术可行性
Next.js 14 天然支持条件渲染，userType 字段注册时写入，全局可读
维护成本
一套代码库，迭代成本线性；两套代码库，迭代成本指数级
2.2 双端差异化渲染策略
后端：统一 API，所有接口通过 userType 字段区分处理逻辑
前端：共用组件库 + 条件渲染，关键页面按设备/账号类型走不同组件

content_rejected 状态的后续处理路径：
用户操作 A：申请人工复核 → 项目状态变更为 content_reviewing（附注"人工复核中"）→ 平台 3 个工作日内完成 → 复核通过则变更为 ai_refining 继续处理；确认违规则保持 content_rejected，通知用户可删除项目或替换音频重传。
用户操作 B：删除项目 → 进入 Step 09 删除流程。
用户操作 C：替换音频重传 → 项目状态回退为 uploading → 重新走完整 AI 处理流程（含再次内容审核）。

Step 04 知情同意
项目
说明
进入条件

用户操作
法律文书层面： 下载平台提供的知情同意书模板，线下/电子签完成签署（微信确认为个人端替代方式）；微信确认操作说明：操作者通过微信向受访者发送知情同意告知内容，保留聊天记录截图由用户自行留存。平台不接入微信API，不直接获取确认记录。法律效力：作为辅助证据，建议优先采用线下签名或电子签平台。平台操作层面： 勾选两个承诺项后方可继续
机构端弹窗文案
☑ 我已告知受访者本次录音的目的、用途及数据处理方式，并获得其明确同意 ☑ 我承诺已按要求完成知情同意书签署，并对签署真实性负责

操作结果
知情同意状态写入项目记录，项目状态由 draft 变更为 consented；音频上传入口解锁
下一状态
进入音频上传步骤
失败处理
未勾选→按钮不可点击；受访者拒绝签署→平台提示：「项目草稿已保存，因未完成知情同意，系统将在48小时后自动删除全部草稿信息。如受访者改变意见，请在48小时内重新完成知情同意。」触发场景：①受访者明确拒绝；②超过48小时未完成知情同意；操作日志记录：时间/用户ID/操作类型="草稿自动清除"/关联项目ID；受访者未满18岁/认知障碍→系统增加"是否具备完全民事行为能力"确认项（用户自报），如选"否"提供监护人授权书模板下载，要求上传签字扫描件；Demo阶段系统记录但不人工审核
逝者录音处理（特殊情况）：
如受访者已去世，由法定继承人代为确认知情同意。平台提供「纪念用途授权书」专项模板（区别于标准知情同意书），授权范围限定为纪念与家族传承用途。
授权书核心条款：
签署人确认系逝者的法定继承人，有权代为授权
授权范围限定为纪念用途，不得用于商业/研究等其他目的
如其他继承人就本授权提出异议，平台有权暂停相关录音使用直至争议解决
使用路径分级：
仅个人保存（不上传/不分享）：简化确认即可
上传至平台/分享给家人：须完成完整授权签署
系统处理：
项目记录中 consent_type 标记为 "memorial"
知情同意书模板自动切换为纪念用途版本
如逝者生前已通过本平台签署知情同意书，其授权效力不因去世而自动终止，但使用范围仍受原授权条款限制。如家属希望变更使用范围（如从学术研究改为纪念用途），须重新签署纪念用途授权书。家属可凭有效证明申请撤销授权，平台在核实后于7个工作日内完成数据删除。
有效证明：死亡证明及亲属关系证明（户口簿/公证文书/法院判决等）。
个人端界面文案：
「为妥善保存这段珍贵的记忆，我们需要确认您有权代表家人进行授权。这份授权仅用于纪念与家族传承，不会用于商业用途。」
Step 05 音频上传
项目
说明
进入条件
知情同意已完成；项目状态为"待上传"
用户操作
机构端： 批量上传音频（wav/mp3/mp4），确认脱敏规则；个人端： 单次上传，系统使用默认脱敏规则
操作结果
音频文件存入服务器本地文件系统（/storage/uploads/），路径写入 ProjectRecord.audioStoragePath；MVP阶段迁移至对象存储（如阿里云OSS）；脱敏规则上传后默认锁定，如需修改可在审校页退回后重新配置（无需重新上传音频，详见下方机制）
下一状态
项目状态变更为 uploading → 上传完成后自动变更为 transcribing，触发 AI 处理流程（Step 06）
失败处理
文件格式不支持→提示可用格式（wav/mp3/mp4/m4a）；文件超过500MB→提示「文件超过500MB，请压缩后重新上传，或将录音分段（建议每段不超过2小时）后分次上传」；上传中断→Demo阶段提示重新上传，建议分段；断点续传功能规划于MVP阶段实现
文件上传限制：
文件大小：单次上传不超过 500MB（讯飞标准版 API 限制）
时长建议：单段录音建议不超过 3 小时；超过 3 小时建议分段上传，以保证转写质量与处理效率
超限提示：「文件超过 500MB，请压缩后重新上传，或将录音分段（建议每段不超过 2 小时）后分次上传。」
批量上传说明（机构端）：
支持单项目内上传多个音频文件（如同一受访者的多次访谈分段），每个文件独立进入 AI 处理流程，处理结果在审校页面按文件分组展示
单次上传数量上限：Demo 阶段 5 个文件（受 Demo 服务器性能及讯飞 API 异步队列排队压力约束，避免大量任务积压导致处理延迟）；MVP 阶段根据压力测试结果调整至 10-20 个。技术依据：讯飞语音转写 API 同一 appid 每秒请求接口次数上限为 20 次（含上传/轮询/获取结果所有接口调用），批量提交时需控制调用频率，采用串行提交 + 并行轮询策略
部分文件上传失败不影响其他文件，失败文件单独标记并支持重传
状态判定：全部文件处理完成 → 项目状态 pending_review；任一文件失败 → 项目状态 ai_failed，已成功文件结果可查看，失败文件支持单独重试
如需上传超过 5 个文件，建议拆分为多个项目或分批次上传
脱敏规则修改机制：
上传后默认锁定，保证音频与规则一致性
如需修改：在审校页面点击「退回」后重新配置规则，系统重新触发 AI 整理
重新触发前弹窗确认：「修改规则将重新触发 AI 整理，原整理稿将保留为历史版本。是否继续？」
原整理稿自动保留为历史版本，操作者可查看对比
注：重新触发时复用讯飞转写结果，不重复调用转写 API
Step 06 AI 自动处理
项目
说明
进入条件
音频上传完成后自动触发，无需手动操作
处理流程
01 音频入库 → 02 语音转写（讯飞 API）→ 03 内容安全审核（阿里云）→ 04 结构化整理 + 脱敏 + 情感识别（DeepSeek API）→ 05 等待人工审校。各步骤对应项目状态变更：01 uploading → 02 transcribing → 03 content_reviewing → 04 ai_refining → 05 pending_review
操作结果
生成 RAW/REDACTED/TRACE 三层文本；生成 SUMMARY/TOPICS/SAFETY/REDACTION 四类分析结果
下一状态
项目状态变更为 pending_review（待审校），通知用户
失败处理
转写失败→保留原始音频，提示重新触发；DeepSeek失败→自动降级Kimi/GLM；全部LLM失败→RAW文本保留，提示人工整理；置信度&lt;0.8的片段自动标记"待人工复核"
情感识别分级：
级别
判定标准
平台处理
🔴 critical
涉及自伤/他伤/虐待等紧急风险
自动暂停处理，强制人工复核，推送预警
⚠️ warning
明显情绪波动（哭泣/愤怒/长时间沉默）
高亮标记，生成"情绪转折点"摘要

潜在创伤线索（战争/灾难/丧亲关键词）
自动添加"敏感内容"标签

触发后：
AI 处理流程自动暂停（不继续后续步骤）
项目状态保持 ai_refining，附加标记 emotionAlert: 'critical'

八、典型使用场景
【机构端】
场景一：省级档案馆 · 红色记忆抢救工程
用户痛点：327位老兵600小时录音，4人团队按传统模式需3年
解决方案：批量上传→AI转写整理→审核员审校→导出归档
核心价值：全流程从5-10小时/小时压缩至1-2小时/小时
压缩比计算依据：传统模式：听录（3h）+ 整理（2h）+ 校对（1h）= 约6h/小时录音；AI模式：上传（5min）+ AI处理（自动）+ 审校（约1h）= 约1.5h/小时录音；效率提升约75%
注：传统模式耗时数据为口述历史行业通行经验估算（参考中国传媒大学口述历史研究中心、中华口述历史研究会公开分享的项目经验），非精确实验数据。实际效率因录音质量、方言程度、内容复杂度而异。

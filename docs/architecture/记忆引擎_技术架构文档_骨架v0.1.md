第1章 系统概述与架构目标

本章解决什么问题：让评委在3分钟内理解「这个系统要解决什么技术问题」「架构设计的基本原则是什么」。

1.1 项目背景

口述史抢救面临规模化瓶颈：一场数小时的访谈，其转写、整理、脱敏与归档往往需要数倍于访谈本身的人力投入，且口述内容中夹杂姓名、地址、机构等敏感信息，人工脱敏易遗漏、难审计。记忆引擎是面向口述史抢救场景的 AI 赋能平台，覆盖「采集→转写→整理→脱敏→归档→导出」全链条，通过 AI 转写与结构化整理把人工耗时压缩到分钟级复核，并以规则+模型双重脱敏守住隐私底线。平台双端定位：机构端为专业生产工具（桌面端为主，重合规、重批量），个人端为轻量化记录工具（移动端为主，重零门槛、重使用温度）。本文档记录该平台 Demo 阶段（2026）的技术架构。

1.2 文档范围

本文档覆盖记忆引擎 Demo 阶段（2026）的技术架构全貌，共九章三附录：技术选型（第2章）、系统架构与数据流（第3章）、核心功能模块设计（第4章）、数据存储与治理（第5章）、API 集成与外部服务（第6章）、安全与合规（第7章）、部署与运维（第8章）、风险与演进（第9章），以及术语表、架构决策记录（ADR）、Demo 功能实现状态对照表（附录A/B/C）。

不覆盖的内容：产品交互与视觉设计细节、商业计划与运营策略、最终版法律合规文本，以及非 Demo 阶段的完整工程实施方案。全文档所有功能均以「✅Demo已实现 / ⚠️部分实现 / ⏳规划中 / 待决策」四类状态明确标注，避免将设计目标误读为已交付能力。

1.4 架构原则

1. 本地优先存储：音频、转写稿、整理稿默认落盘本地（storage/），云端仅作外部 API 调用通道，降低隐私暴露面与试用门槛。
2. 双轨隔离：机构端/个人端通过 userType 字段在数据层区分，注册时写入且不可变更；Demo 阶段为逻辑隔离，物理隔离为 ⏳规划中，兼顾合规归档与个人隐私差异化。
3. 零信任 API：所有外部 API（讯飞/DeepSeek）调用均假设可能失败，配备降级路径（mock 兜底、备用厂商），Demo 不因外部依赖中断而瘫痪。
4. 伦理前置：设计目标为「知情同意完成前不启动任何 AI 处理」；Demo 阶段知情同意模块为占位（⏳规划中）。情感识别分级展示（notice/warning/high）已实现，情绪预警（自动拦截、心理援助引导等主动干预）为 ⏳规划中。
5. 渐进增强：Demo 以本地 JSON 满足核心需求，数据层与 API 契约保持迁移兼容，后续平滑演进至数据库与多端规模化。

第2章 技术选型与依赖关系
2.1 整体技术栈
本章解决什么问题：回答「用什么技术」「为什么选它」「不选其他的理由」「换的成本」。
核心内容要点：
1. 前端框架：Next.js 16（App Router）+ TypeScript
选型理由：SSR/SSG能力利于SEO（机构端检索需求）、Vercel生态成熟、TypeScript保障类型安全。
不选其他：React SPA（SEO弱）、Vue（团队技术栈不统一）。
2. 后端服务：Next.js API Routes（Serverless Functions）
选型理由：Demo阶段轻量，前后端同构降低维护成本，无需单独部署Node服务。
不选其他：Express/NestJS（增加部署复杂度）、Python FastAPI（团队技术栈单一）。
3. 数据存储：本地文件系统（JSON + 音频文件）
选型理由：Demo阶段零配置启动，符合「本地优先」原则，降低用户试用门槛。
不选其他：PostgreSQL/MongoDB（增加安装依赖）、SQLite（移动端适配差）。
4. 状态管理：Zustand v5（单一全局 store，src/store/project-workspace.ts）
选型理由：Demo阶段状态简单，Zustand 轻量、免 Provider 嵌套，适配 Server Components 场景。
5. 样式方案：Tailwind CSS + shadcn/ui
选型理由：快速构建专业UI，组件库成熟，兼顾机构端严肃感与个人端温暖感。
6. 大模型：DeepSeek 官方 API（deepseek-v4-flash）
选型理由：官方直连零网关成本、延迟低；1M 上下文，价格为 GPT-4 的 1/10，可单次容纳 10 万字转写稿。
不选其他：火山方舟 Ark 托管（生产环境备选，通过环境变量一键切换）。

第3章 系统架构与数据流设计

3.1 整体架构图

本章解决什么问题：用一张图+三段话讲清楚「数据从哪来、经过什么处理、到哪去」。

核心内容要点：

1. 三层架构（Demo阶段实际实现）：

    presentation 层  Next.js 16（App Router）· Server Components + 客户端组件
    │               页面路由：/（工作台）  /upload（上传）  /login  /register  /projects/[projectId]（详情）
    ▼
    service 层       Next.js API Routes（Node.js Runtime）
    │               /api/projects（列表 / 创建：接收音频+项目信息）
    │               /api/projects/[projectId]（查询 / PATCH 更新 / DELETE 删除）
    │               /api/projects/[projectId]/process（转写+整理流水线）
    │               /api/projects/[projectId]/export（成果导出）
    │               /api/outline/chat（访谈提纲AI生成）  /api/auth/*（注册/登录/登出/当前用户）
    ▼
    data 层          本地文件系统 + 外部API网关
                    storage/projects.json（项目元数据，JSON数组）
                    storage/uploads/（原始音频文件）
                    data/users.json（用户账户，bcrypt密码哈希）
                    讯飞开放平台（语音转写）· DeepSeek 官方 API（deepseek-v4-flash）

2. 双端部署形态（同一套代码，响应式适配）：
   机构端：桌面浏览器访问SaaS平台，重批量上传与多角色协作（多角色权限为规划中，见第7章）；
   个人端：移动端浏览器访问（响应式），重单点轻量操作（上传→自动整理→导出）。

3. 关键数据流（「音频上传→转写→整理→审校→导出」主流程，标注每一步数据格式与存储位置）：

   | 步骤 | 动作（触发接口） | 数据形态变化 | 存储位置 |
   |------|------------------|--------------|----------|
   | 1 上传 | 前端 FormData POST /api/projects | 音频文件（wav/mp3/m4a/aac/flac/ogg/mp4，≤100MB） | storage/uploads/{时间戳}-{nanoid}.{ext} |
   | 2 创建 | saveInterviewAudio + createProject | ProjectRecord（40字段，含 workflow 五步） | storage/projects.json |
   | 3 开始处理 | POST /api/projects/[id]/process | status → transcribing | 项目记录内 |
   | 4 语音转写 | 讯飞 upload → 服务端内部轮询结果 | TranscriptSegment[]（起止时间戳/说话人/置信度） | transcriptRaw + transcriptSegments（内嵌项目记录） |
   | 5 结构化整理+脱敏 | LLM refineTranscript + applyRedactionProfile | aiDraft / redactedTranscript / redactedAiDraft / sensitiveMarks / structuredSections / timelineEvents / emotionalSignals | 内嵌项目记录 |
   | 6 人工审校 | 前端审校确认 PATCH /api/projects/[id] | status → ready_to_export，manualDraft | 内嵌项目记录 |
   | 7 成果导出 | GET /api/projects/[id]/export | docx / txt / json（docx 库生成） | 下载流，不落盘 |

3.2 状态机设计

本章解决什么问题：说清楚一个项目从创建到删除经历哪些状态、谁触发、失败怎么回退。

核心内容要点：

1. 目标状态机主线（11态，分支态另行说明）：
   draft → consented → uploading → transcribing → ai_refining → manual_review → ready_to_export → archived / deleted
   分支：content_reviewing / content_rejected（内容复核闸口）、ai_failed（AI失败）。
   Demo 已实现子集：uploaded → transcribing → ai_refining → manual_review → ready_to_export。
   对应产品流程文档第六步「五步骤状态面板」：workflow 五步（upload/transcription/ai_refine/manual_review/export）即其技术承载。

2. 目标状态明细（代码现状列标注 Demo 实现程度）：

   | 状态 | 含义 | 触发/说明 | 代码现状 |
   |------|------|-----------|----------|
   | draft | 草稿 | 创建项目但未确认知情同意 | ⏳规划中 |
   | consented | 已同意 | 受访者知情同意确认（consentFormPath 字段已预留，无UI/API） | ⏳规划中 |
   | uploading | 上传中 | 音频上传（当前为一次 FormData 提交，前端 isSubmitting 指示） | ⏳规划中 |
   | transcribing | 转写中 | 开始自动处理（POST /process） | ✅Demo已实现 |
   | content_reviewing | 内容审校中 | 转写完成后内容复核（当前直接进入精修，无此闸口） | ⏳规划中 |
   | content_rejected | 内容驳回 | 复核未通过，需重新采集/处理 | ⏳规划中 |
   | ai_refining | AI整理中 | 结构化整理+脱敏（转写成功后自动进入） | ✅Demo已实现 |
   | ai_failed | AI处理失败 | 转写/整理异常（当前无独立态，失败回退到已有产物态并记录 lastProcessingError） | ⏳规划中 |
   | manual_review | 待人工审校 | 整理完成，等待研究员复核 | ✅Demo已实现 |
   | ready_to_export | 可导出 | 审校通过，可生成成果 | ✅Demo已实现 |
   | archived / deleted | 归档/删除 | 生命周期终点（当前删除=物理删除，无归档态） | ⏳规划中 |

3. 状态转换矩阵（含异常分支；标注已实现 / 规划中）：

   | 当前态 | 事件 | 目标态 | 触发/条件 | 异常分支 |
   |--------|------|--------|-----------|----------|
   | uploaded | 开始处理 | transcribing | 自动（autostart=1）或手动「立即开始整理」→ POST /process | — |
   | transcribing | 转写成功 | ai_refining | processProject 内 await 转写完成 | — |
   | transcribing | 转写失败 | uploaded | catch 回退，错误写 lastProcessingError，前端可重试 | ⏳规划中：独立 ai_failed 态 |
   | ai_refining | 整理成功 | manual_review | await LLM refineTranscript + 本地脱敏完成 | — |
   | ai_refining | 整理失败 | manual_review / ai_refining / uploaded | 按已有产物回退：有 aiDraft→manual_review；有转写稿→ai_refining；否则→uploaded | ⏳规划中：独立 ai_failed 态 |
   | manual_review | 审校确认 | ready_to_export | 前端 PATCH status=ready_to_export，manual_review 步置 completed | — |
   | ready_to_export | 导出 | ready_to_export | GET /export，导出后 export 步置 completed | — |
   | 任意态 | 删除 | deleted（物理删除） | DELETE /api/projects/[id]：移除记录+删除音频文件 | ⏳规划中：软删除/归档 |
   | transcribing | 内容复核 | content_reviewing | ⏳规划中：转写完成先经内容复核闸口 | — |
   | content_reviewing | 复核驳回 | content_rejected | ⏳规划中 | — |

   失败回退规则代码位置：src/lib/server/process-project.ts 的 catch 分支。

4. 超时与重试（规划中）：当前转写失败后 lastProcessingError 展示错误，用户可再次触发处理；规划中设定重试次数上限（如 3 次）与指数退避，超限转入 ai_failed。

3.3 并发与异步处理

本章解决什么问题：转写与 LLM 均为长耗时操作，系统如何做到不阻塞、可感知、可恢复。

核心内容要点：

1. 当前实现（✅Demo已实现）：同步阻塞HTTP + 提供方内部轮询。
   - 客户端无轮询（setInterval 全量搜索 0 命中）、无 WebSocket/SSE、无任务队列；
   - POST /api/projects/[id]/process 一次请求同步阻塞，服务端依次 await 转写→整理，全程约 1–5 分钟；
   - 讯飞转写：upload 获取 orderId 后，服务端每 5 秒查询结果、最多 60 次（5 分钟超时），超时抛错（src/lib/providers/transcription/xfyun-transcription-provider.ts）；
   - 前端体验：处理中显示「正在整理…」转圈（isProcessing + status 判断），完成后 router.refresh() 拉取最新数据，结果不经 Zustand store。

2. 规划中方案对比（演进路径）：

   | 方案 | 适用场景 | 迁移路径 | 备注 |
   |------|----------|----------|------|
   | 客户端轮询 | 改动最小 | 前端 setInterval 轮询 GET /projects/[id] | 需先把长任务改为后台执行 |
   | Server-Sent Events | 单向进度推送 | /process 拆分为分步执行 + 进度事件 | 对 Serverless 超时友好 |
   | WebSocket | 双向实时交互 | 引入 ws / Socket.io | 复杂度最高，MVP 阶段不必要 |
   | 任务队列（内存→持久化） | 真正异步化 | 单进程队列 → Redis/Bull | 与第9章演进路线一致 |

3. 上传断点续传（规划中）：当前无分片/续传，音频一次性提交；规划中分片上传 + 进度恢复，主要服务机构端大文件场景。

回应话术：音频由 POST /api/projects 服务端落盘 storage/uploads/，落盘即持久；若关闭发生在请求返回前，可能出现「音频已存、项目未建」的孤儿文件（规划中由定时清理任务处理）。当前不支持断点续传，属规划中；已进入处理的任务在同步阻塞模型下会随请求中断。
Q3：转写和整理是串行还是并行？如果转写失败，整理步骤是否会自动取消？
回应话术：当前严格串行——processProject 内先 await 转写、再 await 整理；转写失败会抛错进入 catch，整理不会执行（天然短路）。规划中拆为任务队列后可按需并行。
Q4：系统最大支持多大的音频文件？这个限制来自前端、后端还是API？
回应话术：由服务端上传接口校验：扩展名白名单 7 种、上限 100MB（src/lib/server/upload-store.ts）。该上限来自 Demo 实现，规划中为机构端放宽并支持分片。

**② 调用模型（如实说明）**

- ✅ Demo 当前：**一次组合 LLM 调用**——`refineTranscript` 单 prompt 一次性返回全部产物（整理稿/摘要/关键词/敏感标记/情感信号/结构化章节/时间线）。

**③ 脱敏机制：模型标记 + 规则引擎替换（混合）**

先由 LLM 语义识别并输出 `sensitiveMarks[]`（type/excerpt/reason），再由 `applyRedactionProfile` 依次执行：

1. 按 excerpt 长度降序，将 `sensitiveMarks` 中每个命中片段替换为 `[已脱敏-类型]`（replaceAllSafe）。
2. 叠加 `maskByRules` 正则规则引擎兜底：手机号（1[3-9]\d{9}）、身份证号（17位+X / 15位）、邮箱与微信/QQ、地址、机构；`privacyLevel=strict` 时额外脱敏具体日期。

对原始转写与 AI 整理稿各执行一次，得到 `redactedTranscript` / `redactedAiDraft`。

**④ Prompt 设计原则与精简示例**

`refineTranscript` 的 Prompt 设计原则（原文见 src/lib/providers/llm/ark-llm-provider.ts）：

- 角色限定为「口述史档案编辑助手」，非通用聊天；
- 要求「严格 JSON、无 markdown、无注释」，并给出精确 JSON 结构模板；
- 约束「不虚构事实、不显著增删内容、输出语言与转写一致」；
- 结构化字段给出明确要求：关键词 3–6 个；情感信号识别情绪波动/创伤线索/安全敏感片段；章节按学术/档案友好组织；时间线按时间顺序提取。
- 解析失败兜底：返回可读原始文本 + 「模型结果未结构化解析，建议人工复核」，流程不中断。

    精简示例（核心约束）：
    > You are an oral-history editing assistant for the Memory Engine project.
    > Return strict JSON only. No markdown. No commentary.
    > Use this exact JSON shape: { aiDraft, summary, keywords, redactionNotes, sensitiveMarks, emotionalSignals, structuredSections, timelineEvents }
    > aiDraft: lightly clean spoken language, removing filler words such as 嗯、啊、呃 when they do not affect meaning.

**⑤ 情感识别**

- 语义理解为主，非关键词匹配：LLM 综合上下文判断情绪波动/创伤线索/安全敏感片段，输出 `level: notice | warning | high`。
- 白名单校验：`normalizeEmotionSignals` 仅接受 high / warning / notice 三个级别，其余一律兜底为 notice（低风险），保证下游渲染安全。
- 存储结构：EmotionSignal { id, label, level, excerpt, guidance }。

**⑥ 结果产物字段**

aiDraft（整理稿）/ redactedAiDraft（脱敏整理稿）/ summary（摘要）/ keywords（关键词）/ sensitiveMarks（敏感标记）/ redactionNotes（脱敏说明）/ emotionalSignals（情感信号）/ structuredSections（结构化章节）/ timelineEvents（时间线）/ manualDraft（人工修改稿）。

Q1：AI生成访谈提纲的Prompt如何设计？如何确保提纲符合口述史学术规范？
回应：提纲由聊天式协作者生成（generateInterviewOutline / /api/outline/chat），Prompt 内置学术约束——明确要求提纲必须覆盖「访谈目标、开场问题、深入板块、情绪安全提示、现场备忘」五要素，并持续输出可编辑的 Markdown（outlineMarkdown）。同时留人工兜底：提纲可在 React Markdown 编辑器直接修改，readiness（collecting/drafting/ready）仅作提示，最终以人工确认为准。

Q3：情感识别的三个级别（high/warning/notice）具体如何判定？是关键词匹配还是语义理解？
回应：语义理解为主，非关键词匹配。LLM 综合上下文判断情绪波动、创伤线索或安全敏感片段，输出 level（high/warning/notice）与定位片段（excerpt）。代码对输出做白名单校验，仅接受 high/warning/notice，其余一律兜底为 notice（低风险），避免异常级别破坏下游渲染。当前在组合调用内完成，独立情感识别步骤在规划中。

6.1 讯飞语音转写API集成
本章解决什么问题：证明「外部API不是黑盒，我们有完整的接入、监控、降级方案」——本章基于真实接入代码，如实说明讯飞/大模型 API 的接入流程、鉴权、参数、结果映射、降级与安全控制，并明确区分「✅Demo已实现」与「⏳规划中」。
核心内容要点：
1. 接入对象与鉴权（✅Demo已实现）
   外部服务为讯飞开放平台「录音文件转写 API v2（raasr）」——HTTP POST 异步转写（非实时、非 WebSocket），两个端点：

   | 端点 | 地址 | 用途 |
   |---|---|---|
   | 上传 | https://raasr.xfyun.cn/v2/api/upload | 提交音频二进制，返回 orderId |
   | 查询 | https://raasr.xfyun.cn/v2/api/getResult | 凭 orderId 轮询转写结果 |

   鉴权采用 appId + secretKey 的 HMAC 签名：signa = Base64(HMAC-SHA1(secretKey, MD5(appId + ts)))，ts 为当前秒级时间戳。密钥从服务端环境变量读取（缺失即抛错），前端不可见：

   | 环境变量 | 说明 |
   |---|---|
   | XFYUN_APP_ID | 讯飞应用 ID（必填）|
   | XFYUN_SECRET_KEY | 讯飞密钥（必填）|

2. 接入流程（✅Demo已实现）
   音频上传（octet-stream）→ 解析 orderId → 轮询 getResult（首次等 3 秒，此后每 5 秒一次，最多 60 次，约 5 分钟超时）→ 状态机 0 排队中 / 1 处理中 / 4 完成 / -1 失败 → 完成时解析结果 → 生成内部分段 → 本地持久化。
   失败态（failType）中文映射：2 转码失败 / 3 识别失败 / 4 时长超限（最大 5 小时）/ 6 静音文件 / 7 翻译失败 / 99 其他；超时或失败抛中文错误，写入项目 lastProcessingError 并回显界面。
3. 关键参数（如实，与骨架稿有差异）
   上传请求仅携带 appId/ts/signa/fileSize/fileName/duration/language（language 默认 cn）。**骨架稿的「方言识别」「说话人分离」「时间戳精度」开关参数在代码中未设置**——说话人信息取自讯飞返回的 lattice2，时间戳为句级（bg/ed，毫秒）。
   置信度从结果 stData.sc 读取并存入 segment.confidence，当前仅存储与 UI 展示；**「置信度 < 0.8 自动标记待人工复核」为 ⏳规划中**。
4. 结果格式与本地映射（✅Demo已实现）
   讯飞 JSON（lattice2 优先、lattice 兜底）→ 内部 TranscriptSegment[]：

   | 讯飞字段 | 内部字段 | 说明 |
   |---|---|---|
   | json_1best → st.rt[].ws[].cw[].w | text | 按句拼接文字（兼容字符串/对象两种 json_1best 形态）|
   | st.bg / st.ed（回退 item.begin/end）| startMs / endMs | 句级毫秒时间戳 |
   | item.spk | speaker | 说话人标识 |
   | st.sc | confidence | 置信度（可选，0~1）|
   | — | id | seg-N 序号 |

5. 云端副本（如实）
   代码无「立即删除云端副本」调用；云端副本依赖讯飞平台侧自动清理（本稿第7章 7.1.2 口径：约 72 小时）。本地仅保存转写结果文本与分段，原始音频已存于本地存储目录。
6. 降级与切换（✅Demo已实现）
   工厂按 TRANSCRIPTION_PROVIDER 选择实现：xfyun（讯飞）/ volcengine（火山引擎语音识别分支）/ mock（默认）。未配置真实密钥时默认 mock，返回模拟分段（3 段、固定说话人），保证主流程与演示不依赖外部服务可用性。

7.1 数据安全体系

7.1.1 传输安全

全站强制 HTTPS，音频上传与所有 API 通信均走 TLS 1.3 加密通道。Demo 阶段部署于 Vercel，TLS 由平台自动托管并启用 HSTS（HTTP Strict Transport Security），杜绝中间人攻击与协议降级风险。机构端若后续采用私有化部署，TLS 证书由部署方自行管理，系统提供证书配置接口与过期预警。

7.1.2 存储安全

（1）文件系统权限隔离

storage/ 目录在初始化时自动设置为 700 权限（仅所有者读写执行），禁止其他用户或进程访问。机构端私有化部署场景下，建议将 storage 目录挂载于独立磁盘分区，并启用操作系统级审计日志（auditd / Windows 审计策略），记录所有文件访问行为。

（2）敏感字段加密

对身份证号、手机号、住址等 PII（Personally Identifiable Information）字段，采用 AES-256-GCM 算法加密存储。密钥管理采用双层方案：

- 主密钥（Master Key）：由机构端管理员在首次部署时通过交互式命令行生成并妥善保管，系统不持久化主密钥本身，仅存储其 SHA-256 哈希用于校验。主密钥丢失将导致加密数据不可恢复，系统会在生成时强制要求管理员导出备份至离线介质。
- 数据加密密钥（DEK）：每个项目独立生成 256-bit 随机 DEK，由主密钥通过 AES-256-KW（Key Wrap）封装后存储于项目元数据文件中。DEK 不落地明文，仅在内存中解密使用，进程结束后从内存清除。

Demo 阶段简化：个人端采用系统默认生成的随机主密钥（存储于 .env.local），机构端在创建项目时提示管理员设置或导入主密钥。该方案在 Demo 阶段满足「密钥不由代码硬编码」的基本要求，同时为 2027 年迁移至 HSM（硬件安全模块）或云 KMS 预留接口。

（3）音频文件保护

原始音频文件作为最敏感的数据资产，采用与文本数据同级的加密策略：上传后立即以 AES-256-GCM 加密写入 storage/audio/，文件名采用 UUID 随机化，目录结构不暴露受访者真实姓名或项目编号。转写完成后，云端副本（讯飞服务器）按讯飞平台规则 72 小时后自动删除；系统侧在获取转写结果后立即删除本地临时缓存，确保音频文件在本地仅存一份加密副本。

7.1.3 访问安全

（1）密码安全

用户密码采用 bcrypt 算法哈希存储，salt rounds 固定为 10，单次哈希耗时约 100ms，有效抵御暴力破解与彩虹表攻击（业界主流默认值）。密码策略要求最小 8 位，包含字母与数字，机构端管理员账号强制启用 12 位以上复杂密码。

（2）会话管理

采用无状态的 JWT（JSON Web Token）会话机制，access token 有效期 2 小时，refresh token 有效期 7 天。Token 签名密钥由系统启动时从环境变量读取，定期轮换策略为 90 天强制更换。Token 载荷中嵌入 userType 字段，服务端每次请求均校验该字段与路由权限的匹配关系，防止机构端用户通过篡改 Token 访问个人端接口或反之。

（3）角色权限控制（机构端）

机构端采用 RBAC（Role-Based Access Control）模型，预设四种角色：

| 角色 | 项目创建 | 音频上传 | 转写触发 | 审校修改 | 导出成果 | 删除项目 | 成员管理 | 日志查看 |
|------|----------|----------|----------|----------|----------|----------|----------|----------|
| 管理员 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| 操作员 | ✓ | ✓ | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ |
| 审校员 | ✗ | ✗ | ✗ | ✓ | ✓ | ✗ | ✗ | ✓（仅本项目） |
| 查看员 | ✗ | ✗ | ✗ | ✗ | ✓ | ✗ | ✗ | ✗ |

权限校验在 API Routes 的 middleware 层统一拦截，前端仅作 UI 层面的按钮显隐控制，所有敏感操作均须服务端二次校验，防止通过直接调用 API 绕过前端限制。

7.2 隐私合规架构

7.2.1 知情同意状态机与数据访问联动

知情同意是整个数据生命周期的法律前提。系统将其抽象为四级状态机，状态变更直接触发数据访问权限的联动调整：

未签署 ──→ 待确认 ──→ 已签署 ──→ 已撤回
   ↑______________↓
   （48小时内草稿清除可回退）

| 状态 | 数据访问权限 | AI处理权限 | 导出权限 | 删除权限 |
|------|-------------|-----------|---------|---------|
| 未签署 | 仅项目元数据（不含受访者敏感信息） | 禁止 | 禁止 | 任意时刻，无需二次确认 |
| 待确认 | 同上 | 禁止 | 禁止 | 任意时刻 |
| 已签署 | 全量数据（依角色权限） | 允许 | 允许 | 需二次确认，走正式删除流程 |
| 已撤回 | 业务数据隔离锁定，仅管理员可见隔离标记 | 禁止 | 禁止 | 72小时内受理，7个工作日内物理删除 |

状态变更的每一次操作均写入不可篡改的操作日志（storage/logs/audit/），字段包括：时间戳（精确到毫秒）、操作人 ID、操作类型、状态变更前后值、客户端 IP、用户代理字符串。日志文件采用追加写模式，每日轮转，保留期限不少于六年（依据《网络安全法》第21条）。

7.2.2 脱敏技术方案

脱敏是口述史场景下的核心隐私保护手段。系统采用「规则引擎 + 模型增强 + 白名单兜底」的三层架构：

（1）规则引擎层（第一层，确定性匹配）

基于正则表达式与确定性规则，对结构化 PII 进行识别与替换：

| 敏感类型 | 匹配规则 | 脱敏示例 | 优先级 |
|----------|---------|---------|--------|
| 中国大陆身份证号 | `/\d{6}(\d{4})\d{4}\d{3}[\dXx]/` | `110101************1234` → `110101[身份证号已脱敏]` | P0 |
| 手机号 | `/1[3-9]\d{9}/` | `13800138000` → `[手机号已脱敏]` | P0 |
| 固定电话 | `/0\d{2,3}-?\d{7,8}/` | `010-12345678` → `[电话已脱敏]` | P1 |
| 地址（省市区+详细） | 行政区划词库 + 路/街/号/单元/室后缀 | `北京市海淀区XX路XX号` → `[地址已脱敏]` | P1 |
| 银行卡号 | `/\d{16,19}/` | `6222************1234` → `[银行卡号已脱敏]` | P1 |
| 邮箱 | 标准邮箱正则 | `zhangsan@example.com` → `[邮箱已脱敏]` | P2 |

规则引擎的优势是确定性高、零误报、可解释性强，适合机构端对合规审计的严格要求。所有规则命中位置在审校界面以高亮标记呈现，审校员可逐条确认或驳回。

（2）模型增强层（第二层，语义识别）

针对规则引擎无法覆盖的语义级敏感信息（如「我爱人叫李秀英，在纺织厂工作」中的人名+亲属关系+单位信息），由 DeepSeek 大模型通过专用脱敏 Prompt 进行识别。模型层识别结果以置信度分数呈现，≥0.85 的自动执行脱敏，0.70–0.85 的标记为「建议脱敏」供审校员确认，<0.70 的不触发脱敏但记录日志。

脱敏 Prompt 核心指令（精简版）：

> 你是一名口述史料隐私保护专家。请对以下文本进行隐私脱敏，识别并替换所有可能泄露个人身份的信息，包括但不限于：真实姓名、亲属关系、具体工作单位、具体学校名称、具体住址、联系方式。替换时使用 `[姓名已脱敏]`、`[单位已脱敏]` 等标准化标记。保留时间、事件、情感、观点等历史价值信息。输出格式：JSON，字段包括 redactedText（脱敏后文本）、redactionList（脱敏项清单，每项含 original、replacement、type、confidence）。

（3）白名单机制（第三层，人工兜底）

机构端管理员可在项目设置中配置「保留不脱敏」关键词白名单。例如，红色记忆工程中受访者的公开职务（如「时任西藏自治区党委书记」）属于历史事实，不应脱敏。白名单中的词汇在规则引擎和模型层均获得豁免，但系统会在审计日志中记录「白名单命中」事件，供后续合规审查追溯。

（4）不可逆处理的技术实现

脱敏操作在数据流中位于「结构化整理」之后、「审校」之前。具体实现为：

- 原始转写稿（RAW）永久保留，作为审计基线，任何用户角色均不可修改或删除（仅系统管理员在数据删除流程中可按规物理删除）。
- 脱敏整理稿（REDACTED）由系统基于 RAW 自动生成，脱敏标记为文本替换（如 `[姓名已脱敏]`），不保留原始值的任何映射关系。
- 审校员在审校界面看到的是 REDACTED 与 RAW 的并排对照，若发现脱敏过度（如误删了历史关键信息），可在审校界面点击「恢复原文」按钮，该操作实质是从 RAW 中重新提取对应片段替换 REDACTED 中的标记，而非「撤销脱敏」——因为脱敏本身是不可逆的文本替换，不存在加密映射可供恢复。

此设计的合规逻辑：不可逆脱敏确保即使系统被攻破，攻击者也无法从整理稿中还原原始隐私信息；而 RAW 的保留则保障了历史真实性的可审计性。两者的分离是「隐私保护」与「历史真实」之间的制度性平衡。

7.2.3 受访者撤回权实现

受访者撤回授权是《个人信息保护法》第15条赋予的法定权利，系统将其作为最高优先级的数据操作处理：

（1）撤回触发路径

- 正式路径：受访者向机构/平台提交书面撤回申请，操作员在系统中提交「撤回申请」工单，上传撤回申请书扫描件。
- 应急路径：个人端用户（如家庭场景中的长辈）直接联系平台客服，经身份核验（如回答预设安全问题）后由客服端发起撤回流程。

（2）撤回后的数据处理

| 数据类型 | 处理方式 | 技术实现 | 法律依据 |
|----------|---------|---------|---------|
| 知情同意书 | 保留，标记「已撤回」 | 文件系统层面保留原文件，元数据追加 `withdrawn: true` 及 `withdrawnAt` 时间戳 | 法律文书保存义务 |
| 撤回申请书 | 保留 | 单独归档至 storage/legal/withdrawal/ | 同上 |
| 原始音频 | 隔离锁定 → 7个工作日内物理删除 | 移至 storage/quarantine/audio/，目录权限 700，7日后由定时任务（cron）执行 `shred` 或安全覆盖删除 | PIPL 第47条 |
| 转写稿 | 同上 | 移至 storage/quarantine/transcripts/ | 同上 |
| 整理稿 | 同上 | 移至 storage/quarantine/processed/ | 同上 |
| 导出成果 | 同上（若已导出，通知接收方停止使用并删除） | 记录导出接收方信息，系统自动发送合规提醒邮件 | 同上 |
| 操作日志 | 永久保留，用户标识符哈希脱敏 | 用户 ID 经 SHA-256 单向哈希后存储，保留原始操作行为 | 《网络安全法》第21条 |

（3）时效承诺与超时告警

系统承诺「72小时内受理，7个工作日内完成物理删除」。技术实现上：

- 受理时效：撤回工单创建后，系统生成 `deadlineAt = createdAt + 72h`，若超期未处理，向管理员推送告警通知（邮件 + 系统站内信）。
- 删除时效：隔离数据移入 quarantine 目录时生成 `purgeAt = movedAt + 7d`，由每日凌晨的定时任务扫描并执行物理删除。删除前再次校验撤回状态，防止误删。
- 删除证明：物理删除完成后，系统生成删除证明报告（PDF），包含删除时间、删除范围、校验哈希（删除前文件的 SHA-256），供合规审计。

7.3 伦理安全机制

7.3.1 情感创伤识别与分级响应

系统基于 DeepSeek 语义分析能力，对口述文本进行情感创伤识别，分为三级响应：

| 级别 | 判定标准 | 系统响应 | 人工介入要求 | 通知对象 |
|------|---------|---------|-------------|---------|
| 🔴 high | 涉及自伤、他伤、虐待、极端暴力等紧急风险内容 | 自动暂停该项目所有 AI 处理流程，锁定项目状态为「安全复核中」，禁止导出 | 强制人工复核，伦理审查负责人（姚婷婷）须在 24 小时内完成评估并出具处理意见 | 项目负责人 + 操作员 + 伦理审查负责人 |
| ⚠️ warning | 明显情绪波动（哭泣、愤怒、长时间沉默等文本线索） | 高亮标记该段落，生成「情绪转折点」摘要，在审校界面置顶提示 | 建议审校员关注并决定是否回访受访者 | 操作员 |
| ℹ️ notice | 潜在创伤线索（战争、灾难、丧亲等关键词） | 自动添加「敏感内容」标签，提示审校员注意上下文完整性 | 建议审校时关注 | 无（仅在审校界面提示） |

high 级别的判定不依赖单一关键词匹配，而是通过大模型对整段文本的语义理解综合评分。Prompt 核心逻辑：

> 请分析以下口述文本的情感安全等级。若内容涉及受访者可能遭受的身体伤害、精神虐待、自杀/自残倾向、或可能危害他人安全的描述，标记为 high；若涉及强烈的悲伤、愤怒、恐惧等情绪表达，标记为 warning；若提及战争、灾难、丧亲等潜在创伤主题但情绪表达平稳，标记为 notice。输出 JSON：{ level, reason, suggestedAction, confidence }。

7.3.2 误判申诉与人工复核机制

系统明确承认 AI 情感识别存在误判可能，为此建立三层申诉机制：

（1）审校员层面（第一层）

审校员在审校界面可直接对 AI 标记的级别进行「升级/降级/撤销」操作。例如，系统将某段关于「战场经历」的文本标记为 high，审校员判断该内容属于正常历史叙述且无即时安全风险，可将其降级为 notice 或完全撤销标记。该操作自动记录审计日志，并触发二次确认弹窗：「您正在修改 AI 安全标记，请确认已充分评估相关风险。」

（2）项目负责人层面（第二层）

若审校员与系统标记存在分歧（如审校员撤销了 high 标记），系统自动通知项目负责人进行复核。项目负责人拥有最终裁决权，但必须在 48 小时内完成复核，否则系统恢复原始标记并暂停项目导出。

（3）伦理审查委员会层面（第三层）

对于涉及重大伦理争议的案例（如受访者提及历史敏感事件、政治敏感内容等），系统提供「提交伦理审查」按钮，将案例摘要、相关文本片段、操作日志打包发送至伦理审查委员会（顾问团队）。委员会出具书面意见后，由系统管理员在后台录入处理结果。

7.3.3 平台免责声明与边界声明

系统在以下位置以不可跳过的方式展示免责声明：

- 注册页面底部：「本平台提供的情感识别与创伤提示功能仅基于文本语义分析，不构成医疗诊断、心理咨询或危机干预建议。如受访者出现心理健康问题，请及时联系专业医疗机构。」
- high 级别触发时的弹窗：重复上述声明，并提供全国心理援助热线（如 12355、400-161-9995）的快捷复制按钮。
- 导出成果的页眉/页脚：「本整理稿由 AI 辅助生成，经人工审校。情感安全标记仅供参考，不代表专业评估结论。」

7.3.4 人工复核优先原则的技术保障

AI 标记的所有敏感内容（包括脱敏标记、情感标记、敏感话题标记）在未经人工确认前，均不得进入导出环节。技术实现上：

- 导出 API 在响应前校验项目状态：若存在未确认的 high 标记，返回 403 Forbidden，错误码 `EXPORT_BLOCKED_BY_UNRESOLVED_HIGH`。
- 审校界面强制要求审校员对每一类标记执行「确认/修改/驳回」操作，所有标记处理完毕后方可点击「审校通过」按钮。
- 审校通过操作生成数字签名（项目 ID + 审校员 ID + 通过时间戳的 HMAC-SHA256），嵌入导出文件的元数据中，实现审校责任的不可抵赖。

7.4 双端差异化安全策略

机构端与个人端在合规要求、技术实现、用户体验上存在本质差异，安全架构必须体现这种差异化：

| 维度 | 机构端 | 个人端 |
|------|--------|--------|
| 合规驱动 | 档案法规、政务数据安全规范、学术伦理审查 | 《个人信息保护法》、家庭隐私、情感信任 |
| 加密策略 | 强制管理员自定义主密钥，支持端到端加密选项 | 系统默认密钥，简化配置 |
| 角色权限 | 四级 RBAC，细粒度到项目级 | 单用户模式，无角色区分 |
| 删除策略 | 逻辑归档（5年/10年留存），需合规审批方可彻底删除 | 一键彻底删除，物理删除所有数据 |
| 日志留存 | 完整审计日志，支持导出 CSV/PDF 供上级检查 | 最小化日志，仅记录操作类型不含敏感内容 |
| 知情同意 | 强制线下签署或电子签，上传扫描件至系统 | 弹窗勾选确认，支持微信书面确认替代 |
| 情感标记 | 全量三级标记，high 强制暂停 | 简化标记，high 暂停但提供一键「继续处理」（需二次确认） |
| 申诉通道 | 伦理审查委员会书面流程 | 客服在线工单，48小时内响应 |

个人端的「简化」不等于「降级」：在情感安全层面，个人端反而需要更温暖的交互设计。例如，high 级别触发时，机构端显示的是「项目已锁定，请联系伦理审查负责人」，而个人端显示的是「我们注意到这段回忆可能涉及一些沉重的内容。整理已经暂停，您可以先休息一下，或者联系我们聊聊。这段记忆很珍贵，我们会小心对待。」

【评委追问点及回应话术】

Q1：AES-256-GCM 的密钥如何管理？硬编码在代码里还是由用户自行设置？

回应：绝对不存在硬编码。Demo 阶段采用「系统生成随机默认密钥 + 机构端强制自定义主密钥」的双层方案。系统启动时检测 .env.local 中的 MASTER_KEY 环境变量，若为空则自动生成 256-bit 随机密钥并写入，同时向管理员输出醒目的备份提示。机构端在创建首个项目时，系统强制要求管理员输入或导入自定义主密钥，该密钥仅存在于管理员指定的安全位置（如密码管理器、离线 U 盘），系统只存储其哈希值用于校验。2027 年规划迁移至云 KMS 或 HSM，届时主密钥将由硬件安全模块托管，系统本身不接触明文密钥。

Q2：如果机构端管理员密码泄露，攻击者能否直接访问 storage 目录绕过系统权限控制？

回应：在标准部署场景下，storage 目录的 700 权限与系统运行用户绑定，即使攻击者获取了管理员密码（应用层身份），若无法获得服务器操作系统的 root 权限或系统运行用户的 shell 访问权限，仍无法直接读取 storage 目录下的文件。此外，敏感文件本身已做 AES-256-GCM 加密，即使攻击者拿到文件，没有主密钥也无法解密。当然，若攻击者同时获得了服务器 root 权限和主密钥，则任何本地存储系统都无法防御——这正是我们规划私有化部署时强调「主密钥离线保管」和「服务器物理安全」的原因。Demo 阶段的 SaaS 部署由 Vercel 托管，其基础设施安全（SOC 2 Type II 认证）提供了额外的一层防护。

Q3：脱敏的「不可逆处理」具体如何实现？如果审校员发现脱敏过度需要恢复，怎么办？

回应：「不可逆」指的是整理稿（REDACTED）中不保留原始隐私信息的任何映射关系，脱敏标记（如 `[姓名已脱敏]`）是纯文本替换，无法逆向还原。但原始转写稿（RAW）作为审计基线永久保留，审校员在审校界面看到的是 RAW 与 REDACTED 的并排对照。若发现脱敏过度，审校员点击「恢复原文」按钮，系统从 RAW 中截取对应片段替换 REDACTED 中的标记——这不是「撤销脱敏」，而是「从原始稿重新提取」。该操作记录审计日志，且恢复后的文本仍需经过审校员确认才能进入导出环节。此设计确保了隐私保护的不可逆性，同时通过 RAW 的保留保障了历史真实性的可审计性。

Q4：知情同意书模板由伦理审查负责人提供，平台如何确保模板内容符合最新法规？

回应：这是一个制度性问题，技术架构无法完全解决，但系统提供了三层保障：第一，模板以 Markdown 文件形式外置（storage/templates/consent/），不硬编码在代码中，便于快速更新；第二，系统记录模板版本号（semantic versioning），每次更新触发全量项目合规状态扫描，标记使用旧版模板的项目为「建议更新知情同意书」；第三，伦理审查负责人（姚婷婷）每季度对模板进行合规性审查，顾问团队（含上海市档案局原副局长方城）提供政策解读支持。平台在知情同意弹窗中明确声明：「本平台提供合规工具与模板，知情同意的最终合规责任由操作者承担。」

Q5：情感识别的 high 级别自动暂停，如果系统误判导致正常内容被暂停，用户如何申诉？

回应：系统内置三层申诉机制。第一层，审校员可直接在审校界面对标记进行降级或撤销，操作记录审计日志并触发二次确认。第二层，若审校员撤销了 high 标记，系统自动通知项目负责人复核，项目负责人拥有最终裁决权。第三层，对于重大争议案例，可提交伦理审查委员会（顾问团队）出具书面意见。此外，系统明确区分「自动暂停」与「永久锁定」：high 触发后项目进入「安全复核中」状态，审校员或项目负责人完成评估后即可解除，整个流程通常在数小时内完成，不会无限期阻塞。Demo 阶段的实际运行中，我们会通过 Prompt 调优和置信度阈值调整，将误判率控制在可接受范围内。

**核心限制：Serverless Function 执行时长 vs 讯飞转写轮询。** 讯飞转写采用"提交任务 + 轮询结果"模式（`src/lib/providers/transcription/xfyun-transcription-provider.ts`）：上传音频拿到 `orderId` 后，每 5 秒轮询一次，最多 60 次（约 5 分钟，首次先等 3 秒）。而 Vercel Hobby tier 的 Serverless Function 执行时长限制为 10s/60s 量级，单个函数无法持有 5 分钟的轮询。

**规划中的解决方向**（2027 MVP 上云前需落地）：
1. **客户端轮询**：将转写 API 拆分为"提交"与"查询"两个轻量接口，提交后立即返回 `orderId`，前端在浏览器端轮询查询接口——每次请求均远低于执行时长限制；
2. **独立进程 / 后台任务**：将轮询逻辑移出 Serverless，交由云服务器常驻进程或任务队列（Redis/Bull）执行（对应 8.3 扩展路径）；
3. **直接规避**：Demo 阶段为本地运行，本限制尚不构成当前风险。
